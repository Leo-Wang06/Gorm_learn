## 15.1 `Order`：排序

### 基本用法

```go
// 单列排序
db.Order("age desc").Find(&users)
// SQL: SELECT * FROM `users` ORDER BY age DESC

db.Order("age asc").Find(&users)
// SQL: SELECT * FROM `users` ORDER BY age ASC

db.Order("age").Find(&users)
// SQL: SELECT * FROM `users` ORDER BY age（默认 ASC）
```

### 多列排序

```go
// 先按年龄降序，年龄相同按名字升序
db.Order("age desc, name asc").Find(&users)
// SQL: SELECT * FROM `users` ORDER BY age DESC, name ASC

// 链式添加排序
db.Order("age desc").Order("name asc").Find(&users)
// 效果同上
```

### 安全的结构化排序

当排序字段来自用户输入时（如 API 参数 `?sort=name&order=desc`），不要直接拼字符串。列名和 `ASC`/`DESC` 不能像普通值一样用 `?` 占位符绑定，必须做白名单校验。

```go
import (
	"errors"

	"gorm.io/gorm/clause"
)

// ❌ 危险：用户输入直接拼 SQL
sortField := req.Query("sort")
db.Order(sortField + " desc").Find(&users)

// ✅ 安全：字段和方向都使用白名单
allowedFields := map[string]bool{"name": true, "age": true, "created_at": true}
sortOrder := req.Query("order")
if !allowedFields[sortField] {
	return errors.New("无效的排序字段")
}
if sortOrder != "asc" && sortOrder != "desc" {
	return errors.New("无效的排序方向")
}

db.Order(clause.OrderByColumn{
	Column: clause.Column{Name: sortField},
	Desc:   sortOrder == "desc",
}).Find(&users)
```

> 📌 `clause.OrderByColumn` 是 GORM 的结构化排序表达式；先验证用户输入，再交给它构造列名和排序方向。

## 15.2 `Limit` + `Offset`：分页查询

### 基础分页

```go
// 分页必须使用稳定排序；这里以有主键索引的 id 为例
// 第一页：每页 10 条
db.Order("id ASC").Limit(10).Offset(0).Find(&users)
// SQL: SELECT * FROM `users` ORDER BY id ASC LIMIT 10 OFFSET 0

// 第二页：跳过前 10 条，取 10 条
db.Order("id ASC").Limit(10).Offset(10).Find(&users)
// SQL: SELECT * FROM `users` ORDER BY id ASC LIMIT 10 OFFSET 10

// 第三页
db.Order("id ASC").Limit(10).Offset(20).Find(&users)
// SQL: SELECT * FROM `users` ORDER BY id ASC LIMIT 10 OFFSET 20
```

> 📌 分页时始终指定稳定、可索引的排序键；否则数据库不保证每页记录的顺序。`Limit` 和 `Offset` 的调用顺序可以互换，`db.Offset(20).Limit(10)` 效果相同。

### 取消 Limit

```go
// 传入 -1 取消之前的 Limit/Offset 设置
db.Limit(10).Offset(20).Limit(-1).Offset(-1).Find(&users)
// SQL: SELECT * FROM `users`（无 LIMIT 和 OFFSET）
```

## 15.3 分页封装：通用 Paginate Scope

每次分页都写 `Limit + Offset + Count` 太麻烦了，封装一个通用的：

```go
// Paginate 返回一个 Scope 函数
func Paginate(page, pageSize int) func(db *gorm.DB) *gorm.DB {
	return func(db *gorm.DB) *gorm.DB {
		if page <= 0 {
			page = 1
		}
		if pageSize <= 0 {
			pageSize = 10
		}
		offset := (page - 1) * pageSize
		return db.Offset(offset).Limit(pageSize)
	}
}
```

使用：

```go
var users []User
var total int64

page := 2
pageSize := 10
baseQuery := db.Model(&User{}).Where("age > ?", 18)

// 先查总数
if err := baseQuery.Count(&total).Error; err != nil {
	return err
}

// 再查分页数据（分页必须有稳定排序）
if err := baseQuery.Scopes(Paginate(page, pageSize)).
	Order("id DESC").
	Find(&users).Error; err != nil {
	return err
}

fmt.Printf("第 %d 页 / 共 %d 条, 每页 %d 条\n", page, total, pageSize)
```

### 更完善的封装

```go
type Pagination struct {
	Page     int   `json:"page"`
	PageSize int   `json:"page_size"`
	Total    int64 `json:"total"`
}

// Normalize 统一修正分页参数；调用后 p 会被更新为实际使用的值。
func (p *Pagination) Normalize() {
	if p.Page <= 0 {
		p.Page = 1
	}
	if p.PageSize <= 0 {
		p.PageSize = 10
	}
	if p.PageSize > 100 {
		p.PageSize = 100 // 防止一次查太多
	}
}

func (p Pagination) Scope() func(db *gorm.DB) *gorm.DB {
	return func(db *gorm.DB) *gorm.DB {
		return db.Offset((p.Page - 1) * p.PageSize).Limit(p.PageSize)
	}
}

// 使用：统计和取数从同一个“未分页基础查询”派生，确保筛选条件一致。
func ListAdultUsers(db *gorm.DB, page Pagination, minAge int) ([]User, Pagination, error) {
	var users []User
	page.Normalize()

	baseQuery := db.Model(&User{}).Where("age > ?", minAge)
	if err := baseQuery.Count(&page.Total).Error; err != nil {
		return nil, page, err
	}

	if err := baseQuery.Scopes(page.Scope()).
		Order("id DESC").
		Find(&users).Error; err != nil {
		return nil, page, err
	}
	return users, page, nil
}
```

> 📌 `Scope()` 使用值接收者，因此本身不再修改分页参数；参数修正集中在 `Normalize()`，调用方更容易看出其副作用。

## 15.4 `Scopes` 初识：可复用的查询片段

上一节的 `Paginate` 已经是一个 Scope。这里仅用一个最小示例说明“把固定查询片段命名后复用”的效果；Scope 的签名、闭包参数和组合策略会在第19章系统展开。

`Scopes` 让你把常用的查询逻辑封装成可复用的函数：

```go
// 定义一个 Scope
func ActiveUsers(db *gorm.DB) *gorm.DB {
	return db.Where("status = ?", "active")
}

func AdultUsers(db *gorm.DB) *gorm.DB {
	return db.Where("age >= ?", 18)
}

func RecentUsers(db *gorm.DB) *gorm.DB {
	return db.Where("created_at > ?", time.Now().Add(-7*24*time.Hour))
}

// 使用（可以组合多个 Scope！）
db.Scopes(ActiveUsers, AdultUsers, RecentUsers).Find(&users)
// SQL: SELECT * FROM `users` WHERE status='active' AND age>=18 AND created_at>'2024-01-08'
```

> 📌 Scopes 是第19章的重点内容，但这里先预热一下。`Paginate` 就是最常用的 Scope。

## 15.5 大偏移量分页的性能问题

### 问题

```go
// 第 1000 页，每页 10 条；必须显式排序，才能讨论稳定的分页成本
db.Order("id ASC").Limit(10).Offset(10000).Find(&users)
// SQL: SELECT * FROM `users` ORDER BY id ASC LIMIT 10 OFFSET 10000
// 数据库通常仍需定位并跳过前 10000 条候选记录；Offset 越大，工作量通常越高。
// 具体扫描/回表量取决于执行计划、索引和排序列，使用 EXPLAIN 验证。
```

### 优化方案一：基于索引的游标分页（Keyset Pagination）

```go
// 不用 OFFSET，用上次最后一条记录的 ID 作为起点
var lastID uint = 12345 // 上一页最后一条记录的 ID
db.Where("id > ?", lastID).Order("id ASC").Limit(10).Find(&users)
// SQL: SELECT * FROM `users` WHERE id > 12345 ORDER BY id ASC LIMIT 10

// 封装：cursor 条件和排序字段必须一致，并确保该字段有可用索引
func CursorPaginate(db *gorm.DB, cursor uint, pageSize int) *gorm.DB {
	if pageSize <= 0 || pageSize > 100 {
		pageSize = 10
	}
	return db.Where("id > ?", cursor).Order("id ASC").Limit(pageSize)
}
```

优点：在 `id` 有索引且按 `id` 排序时，通常比大 Offset 更稳定。
缺点：不能随机跳到指定页；并发新增/删除会让前后两次翻页看到的集合发生变化，因此更适合无限滚动而非精确页码展示。

### 优化方案二：两步定位起始键

```go
// 先单独定位起始 ID，再取一页数据；这不是 SQL 子查询，而是两次查询。
var startIDs []uint
if err := db.Model(&User{}).
	Order("id ASC").
	Offset(10000).
	Limit(1).
	Pluck("id", &startIDs).Error; err != nil {
	return err
}
if len(startIDs) == 0 {
	return nil // 已超出最后一页
}

db.Where("id >= ?", startIDs[0]).Order("id ASC").Limit(10).Find(&users)
// 该写法仍有一次 Offset；是否更快取决于索引和是否覆盖索引，必须用 EXPLAIN 验证。
```

### 选择建议

| 场景 | 推荐方案 |
|------|---------|
| 管理后台（数据量 < 10 万） | `Offset + Limit` 足够 |
| 用户端无限滚动（APP/Web） | 游标分页（基于 ID 或时间） |
| 管理后台（数据量 > 10 万） | 优先评估游标分页；确需跳页时结合索引、EXPLAIN 和搜索方案 |

## 常见错误

### 错误1：分页忘记排序

```go
// ❌ 没指定排序，分页结果不确定
db.Limit(10).Offset(20).Find(&users)
// 每次查询的"第3页"可能是不同的数据！

// ✅ 始终加 Order
db.Order("id desc").Limit(10).Offset(20).Find(&users)
```

### 错误2：Offset 过大导致慢查询

```go
// ❌ 第 10000 页：排序后仍要跳过大量候选记录
db.Order("id ASC").Limit(10).Offset(100000).Find(&users)
// Offset 很大时通常更慢；具体成本以 EXPLAIN 为准。

// ✅ 可改用游标分页：条件、排序和索引字段保持一致
db.Where("id > ?", lastID).Order("id ASC").Limit(10).Find(&users)
```

### 错误3：在已分页的查询对象上统计

```go
// ❌ 把统计和分页混在同一条已加 Limit/Offset 的链上
// GORM 的 Count 会处理 Limit/Offset，但这种写法不利于复用、阅读和扩展。
query := db.Model(&User{}).Where("age > ?", 18).Limit(10).Offset(20)
var count int64
query.Count(&count)

// ✅ 从同一个“未分页基础查询”分别派生统计和列表查询
baseQuery := db.Model(&User{}).Where("age > ?", 18)
if err := baseQuery.Count(&count).Error; err != nil {
	return err
}
if err := baseQuery.Order("id DESC").Limit(10).Offset(20).Find(&users).Error; err != nil {
	return err
}
```

> 📌 这样可以确保 Count 与列表查询使用完全一致的筛选条件；遇到 `Group`、`Distinct`、自定义 `Select` 等更复杂查询时，也更容易单独确认统计语义。

## 本章小结

- `Order("age desc, name asc")` 多列排序
- `Order("id ASC").Limit(10).Offset(20)`：分页必须搭配稳定排序
- `Paginate(page, pageSize)` 封装为 Scope，复用方便
- `Scopes()` 将查询逻辑模块化（第19章系统学习）
- 大偏移量优先评估游标分页（`WHERE id > lastID`）；条件、排序和索引字段应一致
